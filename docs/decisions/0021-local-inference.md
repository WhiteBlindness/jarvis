# 0021. A local model brokered by the Core, with no authority

**Status:** Accepted. Amends ADR 0006 for model-backed conversation and a desktop client only; voice and personal integrations stay deferred. Amended by ADR 0022: a clipboard proposal is submitted with `submit_clipboard_job` and no longer becomes a job goal.

## Context

The runtime decides and acts in Rust, and asks a person before anything with side effects. What it lacked was a reason to talk to it: a model that converses, and a client that is not a terminal. The model is the least trustworthy component imaginable: its output can be steered by anything it reads, including text a person pastes. So the question is not how to give it tools, but how to let a person talk to it without its output ever becoming an instruction.

The obvious place for a model, the Python worker, is the wrong one. The worker is contained (ADRs 0013, 0014, 0018), but its Windows containment still has the registry and screen gaps those ADRs list, and a model needs gigabytes of weights, a GPU driver and memory far beyond the worker's limit. Loading a GPU driver into an AppContainer would undo most of what ADR 0018 achieved.

## Decision

**The Core brokers the model.** The Core starts a model server (llama.cpp's `llama-server`) as a trusted helper, the same way it starts the Session Agent (ADR 0019): from an absolute path in the configuration, never through a shell, with a cleared environment (the variables Windows and the GPU driver need, and nothing named `LLAMA_*`), and on Windows with no child processes, a commit limit and a kill-on-close job so that it dies with the Core (on Linux, `PR_SET_PDEATHSIG` and an address-space limit; GPU drivers may need that limit raised). It is not isolated from the user: it needs the GPU. It listens on `127.0.0.1` only, on a port chosen at each start, and refuses requests without a key the Core generates for that start, except for its health and model-list endpoints, which carry nothing private. Its web interface, built-in agent tools, slot endpoint and model downloads are switched off (`--no-webui --no-agent --no-slots --offline`); tools and metrics are off by default and the cleared environment keeps them off. The Core refuses RPC connections from the server's process from the moment it is started, as it refuses the worker's; unlike the worker check, it matches that one process, not processes it starts (on Windows its job allows none; on Linux nothing stops it from starting one).

**The model has no tools.** No tool definitions are sent, no tool calls are parsed, and nothing the model writes reaches the policy, the approval store, the worker or the Session Agent. A reply is text for a person to read, stored as text and shown as text. The worker never sees the model, and the model never sees the worker.

**One exception, and it is a suggestion.** When a person asks, in their own words, for something to be copied, the reply may contain one fenced block (```` ```clipboard ````) holding one line. The Core reads that block only if the person's last message asks for a copy outside text in quotation marks, guillemets, angle brackets or code fences (`prompt::asks_for_copy`; the Core cannot tell what was pasted without quotation marks, so pasted text can open this gate), and only if the line passes the clipboard allowlist of ADR 0020 with no newline or tab, so that it can be submitted unchanged as a clipboard job (ADR 0022 replaced the goal `copy "<text>"` with `submit_clipboard_job`). The result is a `proposal` field next to the reply. Nothing happens unless the person presses a button to submit it as an ordinary job; the worker plans it, policy requires confirmation (`desktop.clipboard.write` must be opted in), and the person approves the exact text in the approval inbox, bound by its fingerprint. A prompt injection can at most produce a proposal that a person sees in full and must accept twice: the gate is a filter, the approval is the control. In the recorded evaluation, the model did write a clipboard block when a pasted e-mail asked it to, and the request gate suppressed it.

**The Core shapes risky turns, not the persona.** A small model does not reliably follow rules buried in a long persona, so the Core adds them per turn. The clipboard format is described in the system prompt only for a message that asks for a copy (`prompt::asks_for_copy`); every other turn is told it cannot propose one, which leaves the model no example to imitate. A message that may signal a crisis (`prompt::crisis_signals`: self-harm, a medical emergency) gets serious instructions placed last in the system prompt, a lower sampling temperature, and a first sentence written by the Core that the model continues ("Liga já para o 112." for a medical emergency; an acknowledgement for distress), so the reply cannot open with a joke. Both lists are keyword heuristics in Portuguese and English: they reduce harm, they do not detect every case, and the persona still asks for the same behaviour.

**The model is pinned.** The configuration names the model file and its SHA-256. The Core hashes the file before its first load and refuses a file that does not match; a match is remembered for that path, size and modification time, so later loads do not read the whole file again (a same-user process that can write the file and keep both could defeat this, which is within the same-user trust of the threat model). The audit event records the configured hash.

**Conversations are the person's, and deletable.** They live in their own SQLite file (`donna-chat.db` by default), not in the audit database, because a person must be able to delete what they said and the audit log is append-only. Deleting a conversation, or all of them, removes the rows with `secure_delete` on and truncates the write-ahead log, so the text does not linger in either file (a test checks the files' bytes). An optional retention period deletes conversations not updated for that many days. Nothing is remembered between conversations. The audit log records that the model loaded (profile, SHA-256, context size, GPU layers, load time) and why it stopped, as one of a few fixed reasons; the server's own log lines, which could quote what it was sent, go only to the Core's log.

**The RPC interface grows, and stays typed.** RPC version 3 adds `chat_send`, `chat_regenerate`, `chat_poll` (a long poll returning the reply text after a byte cursor), `chat_cancel`, conversation listing, search, reading and deletion, and model status, load, unload and context size. A person's message is `ChatText` (at most 6000 characters and 12 KiB of UTF-8, newlines allowed, no control or invisible formatting characters), so a request fits the 16 KiB frame unless a client escapes every character. A conversation's history is returned whole; a very long conversation can exceed what a client accepts in one response. One reply is generated at a time. Replies are bounded in tokens, bytes (64 KiB) and time. Streaming wakes long polls through a signal of its own, so it does not wake clients waiting on approvals.

**Model text is shown, never obeyed.** Control characters (other than newline and tab) and invisible characters are removed from the model's text as it arrives (`strip_hidden`), so a reply can neither drive a terminal (for example with an escape sequence that sets the clipboard) nor hide content. Chat-template markup in stored messages (`<|`, reasoning and tool tags) is broken up before the conversation is sent, so pasted text cannot open a new turn or role. A person's message (`ChatText`) refuses the same invisible characters, including tag characters and variation selectors that can carry hidden instructions.

**The model server is not strictly decoded.** Invariant 8 (strict decoding) cannot apply to a server whose schema is not ours. Its responses are read leniently but boundedly: header block, chunk, line and body sizes are capped, only the fields read are type-checked, anything unreadable fails the reply, and the decoded text is only ever stored and shown as text.

**Games come first.** With the governor enabled (ADR 0016), the Core stops the model server while a configured game runs (a load in progress is cancelled), which frees its GPU memory, and loads it again once the game has gone and the resume delay has passed. A reply being written is cancelled and kept as far as it got; new messages are refused with a clear reason. `on_game = "fallback"` runs a second, smaller model instead (configured CPU-only in the example).

**A desktop client, outside the Core.** The Donna app (Tauri 2, `apps/donna`) is an RPC client like the CLI. It holds no policy, approvals or state of its own; it renders model text without HTML and never parses it for actions.

## Consequences

- A person can converse with a local model in a desktop app, with the conversation, the model and the GPU on their machine, and nothing the model writes can act.
- The trusted computing base grows by the model server, a large C++ program that parses model output and runs a GPU driver. It runs with the user's token, like the Session Agent, and could do anything the user's account can if it were compromised. We rely on starting it from a configured path with only the flags above, under a job, and on giving it no input but the conversation.
- The server's key is on its command line, so a process running as the same user can read it. Such a process can already use the RPC interface, so this adds no authority.
- A text a person submitted for the clipboard before ADR 0022 became a job goal and an approval argument, which the audit database keeps for good (ADRs 0008, 0020), and deleting the conversation does not delete it. Since ADR 0022 the text is held as a temporary payload that is deleted when its job ends.
- Reply quality, Portuguese spelling and factual accuracy are the model's. The persona (`config/donna/persona.md`) instructs it; the Core does not check it.
- CI cannot run the model or a GPU. Model loading, GPU offload, governor unloading and the app are validated on Windows hardware and listed in `docs/windows-validation.md`.
